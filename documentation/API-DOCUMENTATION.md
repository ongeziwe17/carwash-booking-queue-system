# API Documentation

This document is the human-readable reference for the currently implemented API on `staging`. Controller mappings, request DTOs, service/security behavior, and the generated OpenAPI document are authoritative when implementation details change.

## Base URL

Local development: `http://localhost:8080`

All application operations use `/api/**`. There is no API version prefix yet.

## Swagger / OpenAPI

- Swagger UI: `http://localhost:8080/swagger-ui/index.html`
- OpenAPI JSON: `http://localhost:8080/v3/api-docs`
- Current controller/OpenAPI operation count: **37**

The OpenAPI document is generated by SpringDoc from the running application; no separate hand-authored OpenAPI file is maintained. CI exports `/v3/api-docs` after Maven verification, and `OpenApiQualityGateIntegrationTest` checks controller coverage, named request DTOs, standard error schemas, sensitive-field boundaries, authentication metadata, operation metadata, path parameters, and local component references. The generated document is standard OpenAPI JSON and is the contract to import into tools such as Postman.

The contract authority is:

```text
controller mappings / DTOs / security implementation
                      ↓
             generated /v3/api-docs
                      ↓
        this human-readable reference
```

## Authentication

Public registration and login do not require a token. Every other `/api/**` operation requires:

```http
Authorization: Bearer <JWT>
```

`<JWT>` is a placeholder only. Never commit or share a real access token.

JWT authentication is stateless. A login token is short-lived, identifies the current user, and carries the server-assigned role used to derive authorities. Invalid, expired, tampered, inactive-user, or stale-role tokens are rejected with a safe `401` response.

## Roles and authorization

The current built-in roles are:

| Role | Current API access |
|---|---|
| `CUSTOMER` | Own profile, vehicles, bookings, queue-entry reads, and notifications; service-catalogue reads. |
| `STAFF` | Own profile/notifications plus global vehicle, booking, and queue operational access; service-catalogue reads. |
| `BUSINESS_OWNER` | Staff-style operational access plus global service management and daily reporting. |
| `PLATFORM_ADMIN` | Global administrative/operational access, including user listing, access to other profiles/notifications, service management, reporting, and role assignment. |

Public registration always creates `CUSTOMER`. Clients cannot choose `roleName`, account status, encoded credentials, or other server-controlled user state during registration or profile update. Role assignment is a separate platform-admin-only operation.

Marketplace tenant isolation is **not** implemented. `STAFF` and `BUSINESS_OWNER` operational permissions that are elevated today are therefore global; they must not be interpreted as business- or branch-scoped access.

## Standard response and error conventions

Successful create operations return `201`; successful physical deletes return `204`; update, lookup, lifecycle-action, login, and report operations return `200`. The booking `DELETE` route is intentionally different: it performs cancellation and returns `204`, but does not physically delete the booking.

Every documented API failure uses `ApiErrorResponse`:

```json
{
  "status": 400,
  "code": "VALIDATION_FAILED",
  "message": "Request validation failed",
  "timestamp": "2026-08-09T10:00:00Z",
  "path": "/api/vehicles",
  "fieldErrors": [
    {
      "field": "plateNumber",
      "message": "must not be blank"
    }
  ]
}
```

The codes currently emitted by the API are:

| HTTP | Code | Meaning |
|---:|---|---|
| 400 | `VALIDATION_FAILED` | Bean Validation or validated method parameter failed. |
| 400 | `MALFORMED_REQUEST` | JSON is missing/unreadable, has a wrong type/enum, or contains a rejected unknown property. |
| 400 | `INVALID_PARAMETER` | A typed path/query value cannot be converted. |
| 400 | `MISSING_PARAMETER` | A required query parameter is absent. |
| 400 | `BUSINESS_RULE_VIOLATION` | The request is structurally valid but violates a current domain/service rule. |
| 404 | `RESOURCE_NOT_FOUND` | A requested or referenced resource does not exist. |
| 401 | `INVALID_CREDENTIALS` | Login credentials are invalid; the response does not disclose which credential failed. |
| 401 | `AUTHENTICATION_REQUIRED` | A protected route has no acceptable bearer authentication. |
| 403 | `ACCESS_DENIED` | The caller is authenticated but lacks the required role/permission/ownership. |
| 405 | `METHOD_NOT_ALLOWED` | The route exists but does not support the requested HTTP method. |
| 415 | `UNSUPPORTED_MEDIA_TYPE` | The endpoint does not support the submitted content type. |
| 500 | `INTERNAL_ERROR` | An unexpected failure was safely mapped to a generic response. |

`UNKNOWN_PROPERTY` exists in the internal error-code enum, but the current HTTP handler intentionally surfaces rejected unknown JSON properties as `MALFORMED_REQUEST`; clients should rely on the emitted contract above.

Errors never contain rejected request values, request bodies, Java exception names, stack traces, passwords, encoded credentials, JWTs, authorization headers, or signing secrets.

## Authentication API

| Method | Path | Auth / access | Success | Expected errors | Purpose |
|---|---|---|---|---|---|
| POST | `/api/auth/login` | Public | `200 AuthResponse` | 400, 401, 405, 415, 500 | Exchange email/password for a short-lived bearer token. |
| GET | `/api/auth/me` | Bearer; any authenticated role | `200 UserResponse` | 401, 404, 405, 500 | Return the authenticated user. |

`LoginRequest` fields:

| Field | Contract |
|---|---|
| `email` | Required email string, maximum 254 characters. |
| `password` | Required string, maximum 256 characters; write-only in OpenAPI. |

`AuthResponse` contains exactly `accessToken`, `tokenType`, `expiresInSeconds`, `expiresAt`, and `user`. `tokenType` is `Bearer`; `user` is the bounded `UserResponse` described below. There is no refresh-token, logout, revocation, or server-session endpoint.

## Users

| Method | Path | Auth / access | Success | Expected errors | Purpose |
|---|---|---|---|---|---|
| GET | `/api/users` | Bearer; `PLATFORM_ADMIN` | `200 UserResponse[]` | 401, 403, 405, 500 | List users. |
| GET | `/api/users/{id}` | Bearer; self or `PLATFORM_ADMIN` | `200 UserResponse` | 400, 401, 403, 404, 405, 500 | Get a user profile. |
| POST | `/api/users` | Public | `201 UserResponse` | 400, 405, 415, 500 | Register a customer. |
| PUT | `/api/users/{id}` | Bearer; self or `PLATFORM_ADMIN` | `200 UserResponse` | 400, 401, 403, 404, 405, 415, 500 | Update profile fields. |
| DELETE | `/api/users/{id}` | Bearer; self or `PLATFORM_ADMIN` | `204` | 400, 401, 403, 404, 405, 500 | Delete an eligible user. |
| PUT | `/api/admin/users/{userId}/role` | Bearer; `PLATFORM_ADMIN` | `200 UserResponse` | 400, 401, 403, 404, 405, 415, 500 | Assign a built-in role. |

`CreateUserRequest` accepts `userId` (max 64), `fullName` (max 120), `email` (valid email, max 254), `phone` (max 40), and `password` (max 200 plus the configured password policy). It has no role or account-status field. Duplicate IDs or normalized email addresses return `400 BUSINESS_RULE_VIOLATION`.

`UpdateUserRequest` accepts only `fullName`, `email`, and `phone`; the path `{id}` remains authoritative. `AssignRoleRequest` accepts one required `roleName`: `CUSTOMER`, `STAFF`, `BUSINESS_OWNER`, or `PLATFORM_ADMIN`. The last active platform administrator cannot be demoted or deleted.

`UserResponse` contains `userId`, `fullName`, `email`, `phone`, `accountStatus`, `createdAt`, `lastLoginAt`, and `roleName`. It never contains `password`, `encodedPassword`, `passwordHash`, a signing secret, or internal vehicle/booking/notification collections.

User deletion is rejected while vehicles or bookings still reference the user; associated notifications may be cleaned only after those dependency rules permit deletion.

## Vehicles

| Method | Path | Auth / access | Success | Expected errors | Purpose |
|---|---|---|---|---|---|
| GET | `/api/vehicles` | Bearer; `STAFF`, `BUSINESS_OWNER`, `PLATFORM_ADMIN` | `200 Vehicle[]` | 401, 403, 405, 500 | List all vehicles. |
| GET | `/api/vehicles/{id}` | Bearer; owner or operational role | `200 Vehicle` | 400, 401, 403, 404, 405, 500 | Get a vehicle. |
| POST | `/api/vehicles` | Bearer; customer for self, operational role for any user | `201 Vehicle` | 400, 401, 403, 404, 405, 415, 500 | Create a vehicle for `userId`. |
| PUT | `/api/vehicles/{id}` | Bearer; owner or operational role | `200 Vehicle` | 400, 401, 403, 404, 405, 415, 500 | Update details without changing ownership. |
| DELETE | `/api/vehicles/{id}` | Bearer; owner or operational role | `204` | 400, 401, 403, 404, 405, 500 | Delete an unreferenced vehicle. |

Here, an operational role means `STAFF`, `BUSINESS_OWNER`, or `PLATFORM_ADMIN` under the current global authorization model.

`CreateVehicleRequest` fields are `userId`, `vehicleId`, `plateNumber`, `vehicleType`, `brand`, `model`, `color`, and `notes`. Ownership is a JSON request field, **not** a query parameter. A customer may supply only their own `userId`; elevated operational roles may create for another existing user. `UpdateVehicleRequest` omits both IDs, so the path vehicle ID and existing owner are preserved.

Plate numbers are unique per owner during create and update, compared case-insensitively after trimming. Vehicle deletion returns `400 BUSINESS_RULE_VIOLATION` while any booking still references it.

`GET /api/services` accepts one optional Boolean query parameter, `active`. Invalid Boolean input returns `400 INVALID_PARAMETER`.

New services are active. Activation/deactivation changes that state without changing identity. A service referenced by a booking or queue entry cannot be physically deleted; deactivate it instead. The catalogue is currently global—branch-specific offerings and Marketplace pricing are not implemented.

## Bookings

| Method | Path | Auth / access | Success | Expected errors | Purpose |
|---|---|---|---|---|---|
| GET | `/api/bookings` | Bearer; `STAFF`, `BUSINESS_OWNER`, `PLATFORM_ADMIN` | `200 Booking[]` | 401, 403, 405, 500 | List all bookings. |
| GET | `/api/bookings/{id}` | Bearer; owner or operational role | `200 Booking` | 400, 401, 403, 404, 405, 500 | Get a booking. |
| POST | `/api/bookings` | Bearer; customer for self, operational role for any user | `201 Booking` | 400, 401, 403, 404, 405, 415, 500 | Create a booking. |
| PUT | `/api/bookings/{id}` | Bearer; owner or operational role | `200 Booking` | 400, 401, 403, 404, 405, 415, 500 | Update mutable booking details. |
| DELETE | `/api/bookings/{id}` | Bearer; owner or operational role | `204` | 400, 401, 403, 404, 405, 500 | Cancel the booking; do not physically delete it. |
| POST | `/api/bookings/{id}/confirm` | Bearer; `STAFF`, `BUSINESS_OWNER`, `PLATFORM_ADMIN` | `200 Booking` | 400, 401, 403, 404, 405, 500 | Confirm a created booking. |
| POST | `/api/bookings/{id}/cancel` | Bearer; owner or operational role | `200 Booking` | 400, 401, 403, 404, 405, 500 | Cancel and return the updated booking. |

`CreateBookingRequest` accepts `bookingId`, `userId`, `vehicleId`, `serviceId`, `scheduledDateTime`, and optional `specialRequest` (max 1000). `UpdateBookingRequest` accepts `vehicleId`, `serviceId`, `scheduledDateTime`, and `specialRequest`; it cannot change the booking ID or owner.

`scheduledDateTime` is a local date-time interpreted against the configured application clock/timezone and must be in the future. The referenced user, vehicle, and service must exist; the vehicle must belong to the booking owner; the service must be active. Active bookings sharing an exact scheduled date/time are limited by the configured slot capacity, and the same customer/vehicle cannot have another active booking in that slot.

Ordinary updates are allowed only in `CREATED` or `CONFIRMED`. Confirmation transitions a valid `CREATED` booking to `CONFIRMED`. Cancellation can transition only `CREATED` or `CONFIRMED` bookings, and only while the booking is still in the future and the configured cancellation cutoff remains open. `IN_SERVICE`, `COMPLETED`, and already-`CANCELLED` bookings reject cancellation. Both public cancellation routes use that same cancellation behavior.

There is an internal service-layer physical delete operation for already-cancelled bookings with no queue entry, but no public hard-delete endpoint. Dedicated booking rescheduling is not implemented.

## Queue Entries

| Method | Path | Auth / access | Success | Expected errors | Purpose |
|---|---|---|---|---|---|
| GET | `/api/queue-entries` | Bearer; `STAFF`, `BUSINESS_OWNER`, `PLATFORM_ADMIN` | `200 QueueEntry[]` | 401, 403, 405, 500 | List all queue entries. |
| GET | `/api/queue-entries/{id}` | Bearer; booking owner or operational role | `200 QueueEntry` | 400, 401, 403, 404, 405, 500 | Get a queue entry. |
| POST | `/api/queue-entries` | Bearer; `STAFF`, `BUSINESS_OWNER`, `PLATFORM_ADMIN` | `201 QueueEntry` | 400, 401, 403, 404, 405, 415, 500 | Create and attach a queue entry. |
| PUT | `/api/queue-entries/{id}/position` | Bearer; `STAFF`, `BUSINESS_OWNER`, `PLATFORM_ADMIN` | `200 QueueEntry` | 400, 401, 403, 404, 405, 415, 500 | Manually reposition a waiting entry. |
| POST | `/api/queue-entries/{id}/call-next` | Bearer; `STAFF`, `BUSINESS_OWNER`, `PLATFORM_ADMIN` | `200 QueueEntry` | 400, 401, 403, 404, 405, 500 | Mark this specific waiting entry as called. |
| POST | `/api/queue-entries/{id}/start` | Bearer; `STAFF`, `BUSINESS_OWNER`, `PLATFORM_ADMIN` | `200 QueueEntry` | 400, 401, 403, 404, 405, 500 | Start service for a called entry. |
| POST | `/api/queue-entries/{id}/complete` | Bearer; `STAFF`, `BUSINESS_OWNER`, `PLATFORM_ADMIN` | `200 QueueEntry` | 400, 401, 403, 404, 405, 500 | Complete an in-progress entry. |
| DELETE | `/api/queue-entries/{id}` | Bearer; `STAFF`, `BUSINESS_OWNER`, `PLATFORM_ADMIN` | `204` | 400, 401, 403, 404, 405, 500 | Delete a waiting entry and clear its booking link. |

`CreateQueueEntryRequest` accepts `queueEntryId`, `bookingId`, `serviceId`, and positive `position`. The booking and service must exist and the supplied service must match the booking service. One queue entry is attached to the canonical booking by the current service workflow. `UpdateQueuePositionRequest` contains only a positive `position`.

The lifecycle implemented today is `WAITING → CALLED → IN_PROGRESS → COMPLETED`. Only `WAITING` entries may be manually repositioned or deleted. The endpoint name `/call-next` is historical: it acts on the supplied queue-entry `{id}` and does **not** choose the next eligible customer. Automatic queue sorting/recalculation and true server-selected call-next remain planned work.

`estimatedWaitMin` is calculated from the submitted position and service duration; the configured fallback service duration is used defensively when no positive service duration is available.

## Notifications

| Method | Path | Auth / access | Success | Expected errors | Purpose |
|---|---|---|---|---|---|
| GET | `/api/notifications/user/{userId}` | Bearer; self or `PLATFORM_ADMIN` | `200 Notification[]` | 400, 401, 403, 405, 500 | List recent in-app notifications. |

Results are sorted newest first by `sentAt`, with `notificationId` as the deterministic tie-breaker, and are limited by the deployment-configured recent-item default. The endpoint does not require the requested user ID to exist before an authorized admin lookup; no records therefore produce an empty list rather than a user `404`.

Notifications are currently `IN_APP` only. SMS/email delivery and a broader public notification lifecycle are not implemented.

## Reports

| Method | Path | Auth / access | Success | Expected errors | Purpose |
|---|---|---|---|---|---|
| GET | `/api/reports/daily-summary` | Bearer; `BUSINESS_OWNER`, `PLATFORM_ADMIN` | `200 DailySummaryReportResponse` | 400, 401, 403, 405, 500 | Return booking/queue counts for one date. |

The required `date` query parameter uses ISO `yyyy-MM-dd`, for example `?date=2026-08-09`. A missing date returns `400 MISSING_PARAMETER`; an invalid date returns `400 INVALID_PARAMETER`.

`DailySummaryReportResponse` contains `reportDate`, `totalBookings`, `confirmedBookings`, `cancelledBookings`, `completedBookings`, `totalQueueEntries`, `waitingQueueEntries`, `calledQueueEntries`, `inProgressQueueEntries`, `completedQueueEntries`, and `pendingWorkload`. It is an in-memory operational summary, not a tenant-aware analytics/dashboard API.

## Current runtime policy behavior

Externally visible policy values are deployment-configurable rather than hard-coded:

- maximum active bookings per exact time slot;
- booking cancellation lead-time window;
- application timezone used for booking time validation/policy decisions and queue/notification lifecycle timestamps;
- recent-notification result limit;
- defensive queue fallback service duration.

See [Runtime Policy Configuration](CONFIGURATION.md) for defaults, validation, cutoff semantics, and environment overrides. Configuration is internal; there is no public configuration endpoint.

## Current limitations

- Persistence is in-memory only and uses shared single-JVM coordination rather than database transactions.
- Multi-instance transaction/locking guarantees are not provided.
- Marketplace tenant isolation and business/branch models are not implemented.
- The service catalogue is global, not branch-specific.
- Queue positions are supplied/manually updated; there is no automatic queue-ordering engine or true server-selected call-next workflow.
- Queue/booking lifecycle synchronization is not yet complete beyond the transitions currently implemented.
- Notifications are in-app only; there is no SMS/email provider delivery.
- Payments/refunds are not implemented.
- List APIs do not provide general pagination or sorting; the services list has only its current `active` filter.
- Production observability/health-platform work is not complete.
- No recommendation engine or frontend is implemented in this repository.
- The application is a backend foundation and must not be treated as production-ready SaaS.

Authentication, secure BCrypt credential storage, JWT validation, RBAC, ownership authorization, typed request DTOs, standardized API errors, runtime-policy configuration, Docker CI, OpenAPI validation, and Bruno HTTP acceptance are implemented foundations—not missing limitations.
