# API Documentation

This document is the human-readable reference for the currently implemented API on `staging`. Controller mappings, request DTOs, service/security behavior, and the generated OpenAPI document are authoritative when implementation details change.

## Base URL

Local development: `http://localhost:8080`

All application operations use `/api/**`. There is no API version prefix yet.

## Swagger / OpenAPI

- Swagger UI: `http://localhost:8080/swagger-ui/index.html`
- OpenAPI JSON: `http://localhost:8080/v3/api-docs`
- Current controller/OpenAPI operation count: **68**

The OpenAPI document is generated by SpringDoc from the running application; no separate hand-authored OpenAPI file is maintained. CI exports `/v3/api-docs` after Maven verification, and `OpenApiQualityGateIntegrationTest` checks controller coverage, named request DTOs, standard error schemas, sensitive-field boundaries, authentication metadata, operation metadata, path parameters, and local component references. The generated document is standard OpenAPI JSON and is the contract to import into tools such as Postman.

The contract authority is:

```text
controller mappings / DTOs / security implementation
                      ↓
             generated /v3/api-docs
                      ↓
        this human-readable reference
```

## Authentication

Public registration and login do not require a token. Every other `/api/**` operation requires:

```http
Authorization: Bearer <JWT>
```

`<JWT>` is a placeholder only. Never commit or share a real access token.

JWT authentication is stateless. A login token is short-lived, identifies the current user, and carries the server-assigned role used to derive authorities. Invalid, expired, tampered, inactive-user, or stale-role tokens are rejected with a safe `401` response.

## Roles and authorization

The current built-in roles are:

| Role | Current API access |
|---|---|
| `CUSTOMER` | Own profile, vehicles, bookings, queue-entry reads, and notifications; service-catalogue, availability, discoverable-branch/offering, and branch open-status reads. |
| `STAFF` | Own profile/notifications plus global vehicle, booking, and queue operational access; service-catalogue, availability, discoverable-branch/offering, and branch open-status reads. |
| `BUSINESS_OWNER` | Staff-style operational access plus global service/Marketplace management and daily reporting. |
| `PLATFORM_ADMIN` | Global administrative/operational access, including user listing, access to other profiles/notifications, service/Marketplace management, reporting, and role assignment. |

Public registration always creates `CUSTOMER`. Clients cannot choose `roleName`, account status, encoded credentials, or other server-controlled user state during registration or profile update. Role assignment is a separate platform-admin-only operation.

Marketplace tenant isolation is **not** implemented. `STAFF` and `BUSINESS_OWNER` operational permissions that are elevated today are therefore global; `MARKETPLACE_MANAGE` also does not yet establish per-owner tenant authorization.

## Standard response and error conventions

Successful create operations return `201`; successful physical deletes return `204`; update, lookup, lifecycle-action, login, and report operations return `200`. The booking `DELETE` route is intentionally different: it performs cancellation and returns `204`, but does not physically delete the booking.

Every documented API failure uses `ApiErrorResponse`:

```json
{
  "status": 400,
  "code": "VALIDATION_FAILED",
  "message": "Request validation failed",
  "timestamp": "2026-08-09T10:00:00Z",
  "path": "/api/vehicles",
  "fieldErrors": [
    {
      "field": "plateNumber",
      "message": "must not be blank"
    }
  ]
}
```

The codes currently emitted by the API are:

| HTTP | Code | Meaning |
|---:|---|---|
| 400 | `VALIDATION_FAILED` | Bean Validation or validated method parameter failed. |
| 400 | `MALFORMED_REQUEST` | JSON is missing/unreadable, has a wrong type/enum, or contains a rejected unknown property. |
| 400 | `INVALID_PARAMETER` | A typed path/query value cannot be converted. |
| 400 | `MISSING_PARAMETER` | A required query parameter is absent. |
| 400 | `BUSINESS_RULE_VIOLATION` | The request is structurally valid but violates a current domain/service rule. |
| 404 | `RESOURCE_NOT_FOUND` | A requested or referenced resource does not exist. |
| 401 | `INVALID_CREDENTIALS` | Login credentials are invalid; the response does not disclose which credential failed. |
| 401 | `AUTHENTICATION_REQUIRED` | A protected route has no acceptable bearer authentication. |
| 403 | `ACCESS_DENIED` | The caller is authenticated but lacks the required role/permission/ownership. |
| 405 | `METHOD_NOT_ALLOWED` | The route exists but does not support the requested HTTP method. |
| 415 | `UNSUPPORTED_MEDIA_TYPE` | The endpoint does not support the submitted content type. |
| 500 | `INTERNAL_ERROR` | An unexpected failure was safely mapped to a generic response. |

`UNKNOWN_PROPERTY` exists in the internal error-code enum, but the current HTTP handler intentionally surfaces rejected unknown JSON properties as `MALFORMED_REQUEST`; clients should rely on the emitted contract above.

Errors do not echo request bodies, Java exception names, stack traces, passwords, encoded credentials, JWTs, authorization headers, or signing secrets. Validation errors identify fields and messages without echoing rejected values; resource-not-found and some business-rule messages may include non-secret resource identifiers.

## Availability

| Method | Path | Auth / access | Success | Expected errors | Purpose |
|---|---|---|---|---|---|
| GET | `/api/availability?serviceId={serviceId}&date={YYYY-MM-DD}` | Bearer; all roles through `PERM_SERVICE_READ` | `200 ServiceAvailabilityResponse` | 400, 401, 403, 404, 405, 500 | Return currently bookable exact-start slots for one active service and date. |
| GET | `/api/availability/branches?serviceId={serviceId}&at={RFC3339}[&latitude={lat}&longitude={lon}&radiusKm={km}]` | Bearer; all roles through `PERM_SERVICE_READ` | `200 BranchAvailabilityResponse[]` | 400, 401, 403, 404, 405, 500 | Return effective public branch offerings available for the complete requested service window. |

`serviceId` is a required trimmed identifier with a maximum length of 64. `date` is a required ISO `YYYY-MM-DD` date that must be today or later according to the configured application `Clock`. Unknown services return `404 RESOURCE_NOT_FOUND`; inactive services return `400 BUSINESS_RULE_VIOLATION`. A valid request with no available slots returns `200` with an empty `slots` list.

`ServiceAvailabilityResponse` contains the service ID/name, requested date, actual service duration, configured global slot capacity, and an immutable ascending list of `AvailabilitySlotResponse` values. Each slot contains `startDateTime`, `estimatedEndDateTime`, and positive `capacityRemaining`. Full slots and, for the current date, starts that are not strictly after application time are omitted.

Slots are generated from the global single-location operating start in configured interval steps. The selected service must finish at or before closing; finishing exactly at closing is valid. Capacity is global per exact start across all services and counts every booking whose status is not `CANCELLED`. Service duration does not introduce overlapping bay/staff occupancy between different start times.

Availability is a point-in-time read under the coordinator read lock and does not reserve capacity. Branch-scoped booking creation, same-branch offering changes, and rescheduling remain authoritative inside the coordinator write lock and re-evaluate `BranchAvailabilityDecisionService`; customer/vehicle conflicts remain an additional write-only check. Booking DTOs validate that the branch-local date/time is present and well formed, but future-time and lifecycle-cutoff checks use the selected branch timezone rather than a server-timezone `@Future` comparison. Branch-local booking times must resolve to exactly one valid timezone offset. AVAIL-001 remains unchanged and global.

Branch search requires `serviceId` and offset-aware `at`. The instant is converted independently through every branch's configured timezone, and the offering duration produces an absolute estimated end. If that instant resolves to a branch-local start with two valid offsets during a DST fall-back overlap, the candidate is excluded for either supplied offset because the current booking request carries only a branch-local `LocalDateTime` and cannot select an occurrence. This preserves the contract that every advertised start is representable and accepted by authoritative booking validation. Internal `INVALID_LOCAL_TIME` decisions are not serialized. The complete half-open window must be continuously covered by weekly hours and must not intersect an active temporary closure. `CREATED`, `CONFIRMED`, and `IN_SERVICE` bookings with overlapping half-open windows at the same branch/offering occupy configured capacity; `CANCELLED` and `COMPLETED` do not. Results expose `max(0, concurrentCapacity - occupiedCapacity)` and omit full candidates.

The configured `carwash.policy.booking.slot-interval` is measured from the start of the applicable continuous branch operating window, not from local midnight. Adjacent weekly intervals share the earliest window anchor, intervals separated by a gap start independent grids, and overnight windows remain anchored to their actual local opening date/time. The interval may be any positive whole-minute duration (for example `PT45M`); search, creation, offering changes, and rescheduling all use this same decision.

Latitude and longitude are optional but must appear together; radius additionally requires that origin and is in `(0, 20000]` kilometres. The existing Haversine port calculates raw distance for inclusive filtering and nearest-first ordering; output alone is rounded to two decimals with `HALF_UP`, with `branchId` as the stable tie-breaker. Without an origin, order is `branchId` and `distanceKm` is null. `queueWaitEstimateMin` is the non-negative sum of `WAITING`, `CALLED`, and `IN_PROGRESS` work in that branch only when `at` resolves to the branch's current local date; completed/exited work is excluded and other/future local dates return null.

| POST | `/api/bookings/{id}/confirm` | Bearer; `STAFF`, `BUSINESS_OWNER`, `PLATFORM_ADMIN` | `200 Booking` | 400, 401, 403, 404, 405, 500 | Confirm a created booking. |
| POST | `/api/bookings/{id}/cancel` | Bearer; owner or operational role | `200 Booking` | 400, 401, 403, 404, 405, 500 | Cancel and return the updated booking. |

`CreateBookingRequest` accepts `bookingId`, `userId`, `vehicleId`, required `branchId`, required `serviceOfferingId`, `scheduledDateTime`, and optional `specialRequest` (max 1000). It does not accept `serviceId`: the reusable service is derived from the offering. `UpdateBookingRequest` accepts only `vehicleId`, `serviceOfferingId`, and `specialRequest`; booking identity, owner, branch, and schedule cannot change. A replacement offering must belong to the booking's existing branch. Strict JSON handling rejects removed/immutable fields such as `serviceId`, `branchId`, or `scheduledDateTime` on generic `PUT` as `400 MALFORMED_REQUEST`. Schedule changes use the focused reschedule operation.

`scheduledDateTime` is a branch-local date-time and must be strictly in the future. It must map to exactly one valid offset: DST gaps and ambiguous overlap times are rejected. Offset-aware AVAIL-002 searches likewise exclude both occurrences of an ambiguous local start, so an advertised result never requires occurrence information that this request does not carry. The time must align to the configured interval from its continuous branch operating-window opening. The complete offering-duration window must fit continuous Marketplace hours without intersecting an active closure. The user, vehicle, branch, offering, and reusable service must exist; the vehicle must belong to the booking owner; the branch and owning business plus offering and service must be effectively active. Public discovery is not operational eligibility, so a private active branch may be booked. Capacity counts overlapping active bookings only for the same branch/offering, while same customer/vehicle conflicts remain branch-scoped.

Ordinary updates are allowed only in `CREATED` or `CONFIRMED`, and are rejected while the booking has an active queue entry. Confirmation revalidates operational parent/offering state. Cancellation can transition only eligible future bookings before the configured cutoff. A valid cancellation removes an associated `WAITING` or `CALLED` queue entry, clears `Booking.queueEntry`, and rebalances only the booking's branch. `IN_SERVICE`, `COMPLETED`, and already-`CANCELLED` bookings reject cancellation. Both public cancellation routes use the same behavior; HTTP `DELETE` remains cancellation rather than physical deletion.

Rescheduling is allowed only for a future `CREATED` or `CONFIRMED` booking before the current appointment's configured booking-change cutoff. It re-resolves the canonical owner, vehicle, branch, offering, and derived service, then reuses branch exact-slot conflict/capacity rules while excluding the booking itself. Active queue work blocks rescheduling. A successful move preserves owner, vehicle, branch, offering, derived service, and status and creates a bounded `BOOKING_RESCHEDULED` notification.

The schedule update is committed inside the shared single-JVM write boundary. If booking repository persistence fails, the original mutable schedule is restored. `BOOKING_RESCHEDULED` notification creation occurs afterward and is best-effort: notification failure is logged without rolling back or failing the committed reschedule. There is an internal service-layer physical delete operation for already-cancelled bookings with no queue entry, but no public hard-delete endpoint.

| DELETE | `/api/queue-entries/{id}` | Bearer; `STAFF`, `BUSINESS_OWNER`, `PLATFORM_ADMIN` | `204` | 400, 401, 403, 404, 405, 500 | Delete a waiting entry and clear its booking link. |

`CreateQueueEntryRequest` retains only `queueEntryId`, `bookingId`, and transitional `serviceId`. Branch and offering are never client supplied: the entry inherits both from the canonical confirmed booking. `serviceId` is a consistency field and must match the booking offering's reusable service. Branch/business and offering/service activity plus every association are revalidated. One active entry is allowed per booking. Every entry starts `WAITING`, appends to its branch queue, receives server metrics, and is attached to the canonical booking inside one write boundary. Strict JSON rejects client branch/offering/position injection.

Active positions are unique and consecutive `1..N` independently within each branch. New entries append at branch `N + 1`; completion and physical deletion close gaps only there. Global list order is deterministic by branch then active/position/joined time/ID, while a `branchId` filter cannot return records from another branch. Omitting the filter preserves the current globally authorized operational view until TENANT-001; it is not tenant enforcement.

Booking and queue filters trim and bound the branch ID, reject blank or malformed values with `400`, and reject unknown branches with `404`. Inactive branches remain valid historical lookup/report scopes; lifecycle state blocks new operational work but does not hide existing records.

Queue API responses are detached snapshots built while the coordinator lock is held, so later mutations cannot alter an in-flight response. Updating a global reusable-service duration does not rewrite waits; the selected offering's configured duration is authoritative.

`estimatedWaitMin` is the cumulative offering duration of active entries ahead in the same branch; an entry's own duration and every other branch are excluded. Completed, exited, and physically deleted entries do not contribute; terminal records have zero wait. Offering concurrent capacity is not used for remaining-capacity calculations in OPS-001.

`UpdateQueuePositionRequest` contains one positive `position`. Only `WAITING` entries may move, and the target cannot exceed that branch's active size. A successful move recalculates only that branch. `call-next` requires `branchId`, revalidates canonical associations, and selects that branch's first `WAITING` entry; lower-position `CALLED`/`IN_PROGRESS` entries are skipped. The by-ID call remains an explicit override. Calling does not start service or rebalance; start and completion atomically synchronize booking and queue before notifications/responses.

## Notifications

| Method | Path | Auth / access | Success | Expected errors | Purpose |
|---|---|---|---|---|---|
| GET | `/api/notifications/user/{userId}` | Bearer; self or `PLATFORM_ADMIN` | `200 NotificationResponse[]` | 400, 401, 403, 405, 500 | List recent bounded in-app notifications. |

Results are sorted newest first by `sentAt`, with `notificationId` as the deterministic tie-breaker, and are limited by the deployment-configured recent-item default. The endpoint does not require the requested user ID to exist before an authorized admin lookup; no records therefore produce an empty list rather than a user `404`.
Each response contains scalar `userId`, `bookingId`, `branchId`, and `serviceOfferingId` context plus notification lifecycle fields. It never serializes User, Booking, Queue, Branch, or ServiceOffering aggregate graphs.

Notifications are currently `IN_APP` only. The synchronized `BOOKING_CANCELLED`, `BOOKING_RESCHEDULED`, `SERVICE_STARTED`, and
`SERVICE_COMPLETED` notifications are attempted only after the canonical booking/queue state is committed. For this
phase they are best-effort: a notification persistence failure is logged and does not turn an otherwise successful
lifecycle operation into a failed API response. Durable notification delivery remains later NOTIFY work; SMS/email
delivery and a broader public notification lifecycle are not implemented.

`QUEUE_CALLED` keeps stricter operational semantics: the call transition and notification must both succeed. If
notification persistence fails, the queue entry's status, call timestamp, position, and ETA are restored so a retry
selects the same still-waiting entry rather than advancing the queue.

## Reports

| Method | Path | Auth / access | Success | Expected errors | Purpose |
|---|---|---|---|---|---|
| GET | `/api/reports/daily-summary?date={date}&branchId={branchId}` or `&businessId={businessId}` | Bearer; `BUSINESS_OWNER`, `PLATFORM_ADMIN` | `200 DailySummaryReportResponse` | 400, 401, 403, 404, 405, 500 | Return booking/queue counts for exactly one explicit scope. |

The required `date` uses ISO `yyyy-MM-dd`. Exactly one nonblank bounded `branchId` or `businessId` is required; neither or both returns `400 BUSINESS_RULE_VIOLATION`, and unknown scope returns `404`. A branch report includes only that branch. A business report resolves its owned branches and includes only those records. Current role access remains global and the scope is not a tenant-authorization boundary.

`DailySummaryReportResponse` adds `scopeType`, `scopeId`, and `timezone` to the existing counters. Booking schedules are branch-local `LocalDateTime` values, so branch dates are compared without the server default timezone. A single-timezone business reports that zone; multi-zone businesses return `MULTIPLE_BRANCH_TIMEZONES`. Completion counters remain based on synchronized source aggregates. This is an in-memory operational summary, not tenant analytics.

| GET | `/api/marketplace/branches/discoverable` | `MARKETPLACE_READ` | `200 BranchResponse[]` | List public branches whose branch and owning business are active. |

`CreateBusinessRequest` requires a bounded ID/name, valid contact email/phone, and optional registration number. `CreateBranchRequest` requires a bounded ID/name/address, two-letter country code, latitude `-90..90`, longitude `-180..180`, a valid Java timezone identifier, and an explicit public-discovery flag. Update requests omit IDs and business ownership.

Business and branch records begin active. Business deactivation leaves branch records unchanged but makes them ineffective and undiscoverable; reactivation restores discovery only for active branches that still opt in. Operational booking/queue validation uses effective activity but intentionally ignores public discovery; availability search additionally requires public discovery. Tenant ownership enforcement remains future work.

## Nearby Marketplace Branch Discovery

| Method | Endpoint | Access | Success | Errors | Behaviour |
|---|---|---|---|---|---|
| GET | `/api/marketplace/branches/discoverable/nearby?latitude={lat}&longitude={lon}` | Bearer; all roles via `MARKETPLACE_READ` | `200 NearbyBranchResponse[]` | 400, 401, 403, 404, 405, 500 | Find effective active, public branches near required coordinates. Optional `radiusKm`, `serviceId`, `openAt`, and `sort=distance` filters are composable. |

Latitude is bounded to `[-90, 90]`, longitude to `[-180, 180]`, and optional radius must be greater than zero and at most `20000 km`. A malformed/blank optional identifier is 400; an unknown canonical service is 404; a known service with no matching effective discoverable offering returns an empty list. `openAt` must be an explicit RFC 3339 offset timestamp—server time is never substituted.

Distance is deterministic Haversine straight-line distance using the IUGG mean Earth radius `6371.0088 km`; no maps/routing provider is called. Radius filtering and distance sorting use the unrounded value. `distanceKm` is rounded only for output to two decimal kilometres using `HALF_UP`. Omitted sort uses `branchId`; distance ties use `branchId`. Service filters never fall back to legacy global price/duration, and open filters reuse `BranchScheduleQuery`, including branch timezone and temporary closures. The endpoint remains authenticated under the established `MARKETPLACE_READ` policy; “public” describes discovery visibility, not anonymous access.

## Marketplace Branch Scheduling

| Method | Path | Auth / access | Success | Purpose |
|---|---|---|---|---|
| GET | `/api/marketplace/branches/{branchId}/operating-hours` | `MARKETPLACE_MANAGE` | `200 BranchOperatingHoursResponse` | Return the current timezone and complete weekly schedule; no stored schedule is returned as an empty/closed schedule. |
| PUT | `/api/marketplace/branches/{branchId}/operating-hours` | `MARKETPLACE_MANAGE` | `200 BranchOperatingHoursResponse` | Atomically insert or replace all weekly intervals. |
| GET | `/api/marketplace/branches/{branchId}/closures` | `MARKETPLACE_MANAGE` | `200 TemporaryClosureResponse[]` | List active and cancelled closure records in closure-ID order. |
| POST | `/api/marketplace/branches/{branchId}/closures` | `MARKETPLACE_MANAGE` | `201 TemporaryClosureResponse` | Create an active absolute temporary closure. |
| POST | `/api/marketplace/closures/{closureId}/cancel` | `MARKETPLACE_MANAGE` | `200 TemporaryClosureResponse` | Cancel without deleting closure history. |
| GET | `/api/marketplace/branches/{branchId}/open-status?at=<timestamp>` | `MARKETPLACE_READ` | `200 BranchOpenStatusResponse` | Decide whether the branch is open at the required RFC 3339 instant. |

`ReplaceOperatingHoursRequest` contains a required bounded `intervals` list. Each interval contains `dayOfWeek`, `opensAt`, and `closesAt`; the timezone is never accepted in this request and is always read from the current branch. Multiple intervals per day, closed days, Friday-to-Saturday overnight periods, and Sunday-to-Monday wrapping are supported. Weekly intervals use half-open `[opensAt, closesAt)` semantics. Equal times, duplicates, same-day overlap, overnight overlap, and weekly-boundary overlap return `400 BUSINESS_RULE_VIOLATION`; adjacent intervals are valid.

`CreateTemporaryClosureRequest` contains bounded `closureId`, offset-aware `startAt`/`endAt`, and a bounded nonblank `reason`. Closure timestamps are converted to instants and use half-open `[startAt, endAt)` semantics. IDs are globally unique, `startAt` must precede `endAt`, and active closures for one branch may not overlap. Cancellation changes status to `CANCELLED`; it does not delete the record, and cancelled records no longer affect open status.

`BranchOpenStatusResponse` contains `branchId`, the requested instant, current branch timezone, resolved zoned branch-local date/time, effective-active state, weekly-hours result, temporary-closure result, final `open` decision, and an applicable closure ID/reason when closed by an active closure. The decision requires an active business, active branch, matching weekly interval, and no active covering closure. `publicDiscoveryEnabled` is deliberately not part of the operational decision.

MKT-002 publishes instant and complete-window decisions. AVAIL-002 consumes the complete-window contract; the existing `/api/availability` endpoint remains single-location and unchanged.

## Marketplace Branch Service Offerings

| Method | Path | Auth / access | Success | Purpose |
|---|---|---|---|---|
| GET | `/api/marketplace/branches/{branchId}/offerings` | `MARKETPLACE_MANAGE` | `200 ServiceOfferingResponse[]` | List all stored branch offerings, including inactive/ineffective records, in offering-ID order. |
| POST | `/api/marketplace/branches/{branchId}/offerings` | `MARKETPLACE_MANAGE` | `201 ServiceOfferingResponse` | Create one active offering with explicit branch terms. |
| GET | `/api/marketplace/offerings/{offeringId}` | `MARKETPLACE_MANAGE` | `200 ServiceOfferingResponse` | Retrieve one bounded management view. |
| PUT | `/api/marketplace/offerings/{offeringId}` | `MARKETPLACE_MANAGE` | `200 ServiceOfferingResponse` | Update only price, duration, and configured capacity. |
| POST | `/api/marketplace/offerings/{offeringId}/activate` | `MARKETPLACE_MANAGE` | `200 ServiceOfferingResponse` | Reactivate without recreating the relationship. |
| POST | `/api/marketplace/offerings/{offeringId}/deactivate` | `MARKETPLACE_MANAGE` | `200 ServiceOfferingResponse` | Deactivate without deleting history. |
| GET | `/api/marketplace/branches/{branchId}/offerings/discoverable` | `MARKETPLACE_READ` | `200 DiscoverableServiceOfferingResponse[]` | Return only customer-facing discoverable offerings. |

`CreateServiceOfferingRequest` contains bounded `offeringId` and `serviceId`, explicit non-negative `BigDecimal` price with at most 10 integer and 2 fraction digits, duration `1..1440` minutes, and configured concurrent capacity `1..1000`. The branch comes only from the path. `UpdateServiceOfferingRequest` contains only those three mutable terms; offering identity, branch ownership, service identity, and status cannot be replaced. Duplicate offering IDs and duplicate branch/service pairs return `400 BUSINESS_RULE_VIOLATION`; unknown branches, services, and offerings return `404 RESOURCE_NOT_FOUND`.

Each offering starts `ACTIVE`. Records are activated/deactivated, never physically deleted. `effectiveActive = offering.active AND service.active AND branch.effectiveActive`; `discoverable = effectiveActive AND branch.publicDiscoveryEnabled`. Parent lifecycle changes do not rewrite offering status, so parent reactivation restores effective/discoverable state when the offering remains active. Operating hours do not participate in offering discovery.

`concurrentCapacity` is the configured maximum simultaneous work for that offering. It is not remaining capacity and this API does not inspect bookings, queues, wash bays, or staff rosters. The published `ServiceOfferingQuery` returns detached immutable snapshots—including configured capacity—for OPS-001 and AVAIL-002. Management remains global for BUSINESS_OWNER/PLATFORM_ADMIN until TENANT-001.

## Current runtime policy behavior

Externally visible policy values are deployment-configurable rather than hard-coded:

- maximum active bookings per exact time slot;
- booking cancellation lead-time window;
- global single-location operating start and end;
- booking slot interval;
- application timezone used for booking time validation/policy decisions and queue/notification lifecycle timestamps;
- recent-notification result limit;
- defensive queue fallback service duration.

See [Runtime Policy Configuration](CONFIGURATION.md) for defaults, validation, cutoff semantics, and environment overrides. Configuration is internal; there is no public configuration endpoint.

## Current limitations

- Persistence is in-memory only and uses shared single-JVM coordination rather than database transactions.
- Multi-instance transaction/locking guarantees are not provided.
- Marketplace businesses/branches are in memory and management access is global until tenant isolation is implemented.
- Reusable service definitions remain global; new bookings and queue waits use branch offerings, while AVAIL-001 still uses legacy global service/capacity inputs.
- Operational list filters and report scopes are functional but do not enforce business-owner tenant ownership until TENANT-001.
- Queue/booking lifecycle synchronization is not yet complete beyond the transitions currently implemented.
- Notifications are in-app only; there is no SMS/email provider delivery.
- Payments/refunds are not implemented.
- List APIs do not provide general pagination or sorting; the services list has only its current `active` filter.
- Production observability/health-platform work is not complete.
- No recommendation engine or frontend is implemented in this repository.
- The application is a backend foundation and must not be treated as production-ready SaaS.

Authentication, secure BCrypt credential storage, JWT validation, RBAC, ownership authorization, typed request DTOs, standardized API errors, runtime-policy configuration, Docker CI, OpenAPI validation, and Bruno HTTP acceptance are implemented foundations—not missing limitations.
