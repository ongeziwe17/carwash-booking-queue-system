# Portable deployment reference

This is a Kubernetes/Kustomize reference for the backend. It does not select a cloud, ingress controller, managed database, secret manager, certificate issuer or production cluster. The manifests are **not** a production provisioning script. They require a verified application image digest, externally provisioned PostgreSQL and a runtime Secret before application.

## Runtime and profile matrix

| Profile | Persistence | Bootstrap admin | API documentation | Intended use |
| --- | --- | --- | --- | --- |
| default | In-memory | Disabled unless explicitly configured | Available | Local development only; data disappears on restart. |
| test | In-memory | Disabled | Available to tests | Deterministic automated tests. |
| postgres | PostgreSQL/Flyway | Disabled by default | Available | Local Compose and controlled development. |
| staging | PostgreSQL/Flyway through the profile group | Forced disabled | Disabled | Durable preproduction deployment. |
| production | PostgreSQL/Flyway through the profile group | Forced disabled | Disabled | Durable deployment. |

The `staging` and `production` groups activate `postgres` before their runtime restrictions. An early context initializer rejects a missing PostgreSQL profile, non-PostgreSQL URL, missing database username/password, disabled Flyway, enabled bootstrap administration or API documentation, or an override that excludes database autoconfiguration. It returns one generic startup error without echoing credential values. Local Compose continues to use `postgres`; the deployment reference uses `production`, and the staging overlay uses `staging`. The profiles do not enable external notification/payment providers.

The existing JWT configuration requires a Base64 key decoding to at least 32 bytes. Keep the signing key stable across replicas and rotate it as a coordinated change that invalidates prior tokens. Externalize the JDBC URL, username, password and JWT key in a Secret named `hlambaq-runtime`, with keys `db-url`, `db-user`, `db-password`, and `jwt-secret`. `scrape-user` and `scrape-hash` are separate credentials; the latter must be a `{bcrypt}` hash. No Secret resource or encoded credential is committed. Store the Secret through an approved cluster secret manager or operator, and restrict its readers. Environment variable references work without application changes; if using mounted secret files instead, arrange a trusted launcher/config import that supplies the same Spring properties without copying secrets into the image or logs.

The ConfigMap contains non-secret settings: issuer, password policy, port, profile, pool and trace sampling. Set the JDBC URL to a reachable external PostgreSQL endpoint with TLS and certificate verification according to the database operator's policy; do not point the production deployment at the CI fixture. Use separate credentials and databases per environment. Startup runs Flyway's additive migrations and Hibernate schema validation. Flyway serializes concurrent startup migrations using its schema history lock; grant the migration identity only the necessary privileges, or separate migration ownership operationally after designing and validating a compatible migration process. `clean` stays disabled and validation stays on. V1–V8 remain unchanged.

The optional trace endpoint is empty by default. Configure `CARWASH_TRACE_OTLP_ENDPOINT` only for a trusted collector and transport. Collector failure does not change readiness. Scrape credentials require TLS from the monitoring client to the trusted proxy and restricted network access; management authentication does not query PostgreSQL. Keep diagnostic Actuator endpoints unavailable. No production domain or telemetry provider is required by this reference.

## Image, privilege and sizing

The Dockerfile pins both builder and JRE base indexes by digest and copies only the packaged JAR into the runtime layer. Refresh those digests deliberately with vulnerability scanning and a rebuilt, tested image. The direct Java entrypoint is PID 1 and receives SIGTERM without a shell. The runtime identity is UID/GID 10001, with a read-only application filesystem, no privilege escalation, no Linux capabilities and the runtime's default seccomp profile. Java temporary files and user-home data use a 64 MiB in-memory `/tmp`; no writable application directory or host volume is required. Compose exercises the same read-only/temp model locally.

The initial per-pod request is 250m CPU/512 MiB memory; the limit is 1 CPU/768 MiB memory, plus 64 MiB bounded tmpfs and an ephemeral-storage limit. Java starts with a 20% heap target and caps heap at 55% of detected container memory, leaving room for metaspace, native allocations, threads and the application. Measure peak native memory, GC, latency, temporary storage and migration startup in the chosen infrastructure before adjusting limits. The default two replicas at 10 Hikari connections each can use 20 connections; a rolling surge adds a third replica, so allow at least 30 plus operational headroom. The shared queue gauge is refreshed on each replica from the same database: **do not sum it across replicas**. Aggregate request counters/histograms appropriately, and use per-instance or max/last for snapshot gauges.

The reference has two replicas, `maxSurge: 1`, `maxUnavailable: 0`, and `minAvailable: 1` for voluntary disruptions. It does not guarantee uninterrupted traffic on every cluster. Startup probes allow up to five minutes for image initialization and migrations. Readiness includes PostgreSQL and is checked every five seconds, with a five-second request timeout aligned with the three-second connection timeout; liveness has no DB or telemetry dependency. Kubelet health requests require no database-backed JWT. The application marks readiness refusing traffic during graceful shutdown and waits up to 20 seconds for in-flight work; Kubernetes allows 45 seconds for endpoint propagation and termination. The CI drain test checks a real in-flight HTTP request before completion. Operators must verify ingress/load-balancer drain and rollout availability in their actual environment.

## Traffic and network boundary

The ClusterIP Service exposes port 8080 only inside the cluster. No ingress is installed. The ingress NetworkPolicy permits TCP/8080 from namespaces explicitly labeled `hlambaq-access=gateway` or `hlambaq-access=monitoring`. Only label trusted controller/monitoring namespaces; use a CNI that enforces NetworkPolicy. Kubelet probes use node traffic, which Kubernetes network policy does not filter. The reference deliberately does not select an egress destination: the external database CIDR, DNS resolver, optional collector and any approved outbound integrations differ by environment. Egress remains unrestricted until the operator supplies an enforceable policy for those real destinations. Network policy is not a substitute for database TLS/authentication or an external firewall. The disposable kind test validates manifests and runtime behavior but kind's default CNI is not evidence that ingress policy is enforced.

Terminate HTTPS at a trusted ingress or reverse proxy, restrict direct backend access to that proxy and monitor, remove untrusted incoming `Forwarded`/`X-Forwarded-*` headers, and inject the headers defined by that proxy. The application explicitly uses `server.forward-headers-strategy=none`; public clients cannot set an effective scheme or host by sending those headers to the backend. Configure HSTS and any cookie/redirect behavior at the TLS proxy; verify effective HTTPS redirects, certificate chain, HSTS and secure headers with the eventual ingress. Spring's `nosniff` and frame-denial headers are checked against the actual process in CI. Do not enable wildcard CORS. `/v3/api-docs` and Swagger UI are disabled in staging and production; generate/review OpenAPI in the existing CI/test pipeline instead. `/actuator/prometheus` remains Basic-authenticated with a separate bcrypt identity, while minimal liveness/readiness paths are public only inside the restricted service network.

## Release and rollback

The existing branch promotion remains `staging` → `develop` → `master` → `v*` tag. CI validates Maven, architecture, PostgreSQL, repeatability, API/Bruno, container, vulnerability and deployment reference checks before publishing on permitted pushes. Use unique version/SHA tags; record the registry's immutable **manifest digest**, scan it, and promote the same digest between environments rather than rebuilding from a mutable tag. The committed zero digest is intentionally unusable. Render a copy with an approved digest; keep local rendered files and secrets outside version control.

Preflight: verify the target namespace, external Secret, PostgreSQL backup and connectivity/TLS, available connections for surge, image digest/provenance, migration compatibility and NetworkPolicy enforcement. Inspect current Flyway history, cluster capacity and alerts. Render and server-validate first; then apply and watch the rollout, readiness, 5xx/latency, pool saturation, Flyway logs and queue telemetry. Keep the previous known-good image digest and a tested rollback plan. A failed application rollout may be rolled back to a **schema-compatible** image; an application rollback does not reverse a database migration. Assess old/new application compatibility before applying a migration and before undoing a rollout. Never automatically downgrade a database or delete volumes.

The following commands are examples for a disposable/test context only; select and verify the current Kubernetes context before any state-changing command:

| Command | Effect |
| --- | --- |
| `kubectl kustomize deployment/kubernetes/base > rendered.yaml` | Writes a local rendered production-reference file; makes no cluster change. Replace the zero image digest in that local file with the verified promoted digest. |
| `kubectl kustomize deployment/kubernetes/staging > staging.yaml` | Writes a local staging-reference file using the `staging` profile and namespace; makes no cluster change. |
| `python3 tools/validate-deployment.py rendered.yaml --real-digest` | Reads the local file and checks deployment/security invariants; makes no cluster change. |
| `kubectl apply --dry-run=server --validate=strict -f rendered.yaml` | Asks the selected cluster API to validate the file; persists no resources. The namespace and externally managed Secret must already exist for a full dry run. |
| `kubectl apply -f rendered.yaml` | **Changes** resources in the selected cluster; starts or rolls the application. Use only in an authorized environment after preflight. |
| `kubectl -n hlambaq rollout status deployment/hlambaq-api --timeout=360s` | Waits and reads rollout status; makes no cluster change. |
| `kubectl -n hlambaq rollout undo deployment/hlambaq-api` | **Changes** the application image/config to the previous revision; first establish database compatibility. |

The CI deployment workflow provisions only a disposable kind cluster and ephemeral PostgreSQL, runs two digest-distinct but schema-identical images through rollout/rollback, probes DB failure isolation, and deletes them with the runner. This proves the reference mechanics, not production data recovery, real prior-version compatibility, CNI enforcement, ingress TLS behavior or HA PostgreSQL. Database backups/restore, cluster/node resilience and disaster recovery remain operator work. No payments, external notifications or cloud infrastructure are provisioned here.
